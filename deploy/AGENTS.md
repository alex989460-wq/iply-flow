# Deploy Rules (ZUI/VPS)

- Keep ZUI Player public-site presentation isolated from activation, payment, playlist and admin logic; deploy only reviewed static assets with a rollback copy to prevent functional regressions.
- ZUI version upgrades must exclude installed public-site assets from overwrite/deletion, and admin layout overrides must load only on admin pages, so bundled releases cannot regress the reviewed website.
- Track ZUI web-app and API versions separately; frontend-only releases must not relabel or restart the API, because their compatible versions can legitimately differ.
- Promote a reviewed ZUI web release by copying its static dependencies before atomically replacing the /app/ entry HTML, with protected site/API hashes and a rollback copy; this preserves the public site and avoids restarting operational services.
- Keep deployable ZUI presentation overrides in deploy/zui-presentation and scope admin selectors to site-admin, so reviewed styling is reproducible without changing operational handlers.
- Embed reviewed ZUI presentation CSS and self-contained font faces in the existing served HTML when custom asset routes are unavailable, so typography works under the existing security policy without relaxing it.
- Apply ZUI motion as a site-scoped CSS-only override with reduced-motion support and keep security headers isolated to reviewed Nginx locations, because site polish must not modify device authentication or playback compatibility.
- Keep ZUI backup decompression bounded and test oversized valid archives plus tamper rejection; accumulated static releases can exceed the upstream bound without indicating a wrong encryption key.
- Organize ZUI admin navigation by ordering existing page buttons and adding presentation labels only; preserve all operational listeners and recognize late-loaded admin pages without changing authorization.
- Keep ZUI license Pix as a separate bridge (deploy/zui-efi-pix) wired through ZUI's external HMAC provider and confirmed by polling Efí, so ZUI upgrades don't overwrite it and Super Gestor's Efí webhook stays untouched.
- Serve ZUI media probing from a dynamically-resolving FFmpeg build (installed under /opt/zui-ffmpeg-*, copied to /usr/local/bin with a backup) and test it against a real provider hostname; the johnvansickle 7.0.2 static build segfaults resolving provider domains, silently hiding audio/subtitle tracks.
- Make the ZUI /app mobile layout a presentation-only `<style id="zui-app-mobile">` embedded in the active release's index/login HTML via deploy/zui-presentation/apply-app-mobile.py, scoped to max-width 760px; TV viewports stay untouched and each new web release must be re-applied.
- Back up ZUI to the Super Gestor Telegram with a root systemd timer (deploy/zui-telegram-backup) that snapshots SQLite via VACUUM INTO and gpg-encrypts it plus keys before upload, because ZUI's own .zuibak files exceed Telegram's 50 MB bot limit.
- Block direct public VPS internal-service ports in both IPv4 and IPv6 mangle PREROUTING on the external interface, with a persistent oneshot service and rollback, because Docker bypasses ordinary INPUT rules while local Nginx and container traffic must remain available.
- Serve ZUI legal pages (/politica-de-privacidade, /termos-de-uso) as self-contained HTML generated by deploy/zui-presentation/legal/build.py, with languages switched by legal-i18n.js via dedicated Nginx locations, so adding app languages never touches the installed site-i18n or app assets.
- ZUI code login on Direct-route servers (or installed clients sending requestRoute=direct + clientProviderAuth=1) must register the playlist without VPS confirmation and without partner licence when the provider blocks the VPS; re-apply deploy/zui-login-direct after any ZUI API upgrade, because providers return 403/404/fake auth=0 to datacenter IPs.
- The ZUI /app web release relays HTTP managed-playlist catalogue/M3U requests through /api/device/provider only when not installedClient() on HTTPS (deploy/zui-web-relay, re-apply per web release); installed TV/Android clients keep direct provider access.
- Embed ZUI admin dashboard cards and device filters via deploy/zui-admin-insights/apply.py as a render()/table() wrapper inside admin index.html, reading only the already-loaded device list, so operational handlers and licence rules stay untouched; re-apply after admin HTML upgrades.
- Deploy deploy/zui-admin-insights/presence.mjs alongside zui-pool.mjs and re-apply apply-presence.py after API upgrades; both management views use recent contact or valid playback leases without modifying device entitlements.
- Keep ZUI Pool, partner-server delegation and contacts in deploy/zui-pool (zui-pool.mjs wired into server.mjs by apply-server.py, admin pages via apply-admin.py); pool is count-only over existing playback leases and partner DNS changes reuse the audited migration flow, so playback and licence rules stay untouched. Re-apply after API/admin upgrades.
- Keep optional partnership deadlines in partnership-policy.mjs and enforce them only on delegated management endpoints; device licences and playback remain governed by their existing rules.
- Serve Pool/platform pages and platform marks through dedicated ZUI Nginx static locations, leaving app, public homepage and operational handlers unchanged.
- Keep ZUI customer MAC transfer in deploy/zui-mac-transfer: it swaps only entitlement fields between two registered devices (both proven by MAC+key, max 3 per licence, audited), never device MACs/credentials; re-apply after client.mjs/playlist-portal.js upgrades.
- Force a ZUI device to expired via the persistent device.adminExpiredAt flag checked first in commerce.mjs license(); it is lifted only by a later paid activeUntil or by a partner-code login newer than the flag (device.partnerLoginAt, deploy/zui-license-expire) with a currently valid partner licence, so background revalidation never undoes it. partnerAccessRequired is recomputed by reconciliation and must not be used for this. Re-apply after API upgrades.
